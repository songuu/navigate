# 日历首次加载性能

更新：2026-10-26。本文区分已完成的代码验证和待完成的生产验收，不将热缓存结果当作首次访问性能。

## 原因与改动

旧版日历缓存为 60 秒；缓存过期后的首个请求串行执行三次 `news_items` 全表统计。归档约 2.1 万篇文章时，已测得日历接口首次读取约 29–43 秒。页面已并行请求文章与日历，主要等待发生在后端统计。

[005-news-calendar-rollups.sql](../database/005-news-calendar-rollups.sql) 增加两个持久汇总表：

| 表 | 计数维度 | 用途 |
| --- | --- | --- |
| `news_calendar_buckets` | 采集日期、主题层级 | 日历日期桶与文章数量 |
| `news_calendar_sources` | 主题层级、来源名称 | 各层来源数、跨层去重后的全部来源数 |

`news_items` 的 AFTER INSERT / UPDATE / DELETE 触发器在同一业务事务中调整计数；正文、翻译、阅读量等非维度更新不改写汇总。AFTER TRUNCATE 同步清空汇总。零计数行保留以保持并发锁定目标稳定，读取时统一过滤 `article_count > 0`。计数缺失或异常会使原写入事务失败并回滚，不吞错制造漂移。

[PostgreSQL 读取适配器](../scripts/content-api/postgres-repository.ts) 用一条 SQL、一个 MVCC 快照读取这两个小表，保持原 `buckets` / `sourceCounts` API 结构、日期顺序及来源名称跨层去重语义。缺少迁移会显式失败，不回退为大表统计。

生产还启用就绪前加载和主动日历刷新：先成功读取汇总，服务才监听端口；随后每 30 秒主动刷新同一份内存快照，与访问量无关。前台只读快照，不再等冷连接，也不外套第二层 60 秒日历缓存。列表仍保留原来的 60 秒缓存和刷新语义，网页请求超时不变。后台刷新失败会记录错误、保留上次成功且不延长成功时间；快照超过 120 秒时，日历和健康检查快速返回 503，后台成功后恢复，避免无限期陈旧却报健康。关闭服务清理定时器。

`CONTENT_API_CALENDAR_REFRESH_INTERVAL_MS` 默认 30000，生产上限 30000；`CONTENT_API_CALENDAR_MAX_STALE_MS` 默认 120000。未启用主动模式的通用服务器仍保留原有请求时刷新契约。

只读 API 的 PostgreSQL 连接有 5 秒建立连接、10 秒服务端语句和 12 秒客户端读取限制；失败连接从池中移除，使后台单飞刷新能够重试。采集器的写连接不使用这些新限制。真实只读验证中，`pg_sleep(11)` 在 10.109 秒超时，随后重连和汇总读取在 4.247 秒恢复，仍返回 21003 篇。

刷新成功时还会预先编码 UTF-8 Buffer，与对象和成功时间一起原子发布。日历 HTTP 只检查快照年龄后直接发送该 Buffer，避免每次请求遍历 849 个日期桶或在并发访问时重复序列化。序列化失败保留旧快照，不发布半成品。

## 迁移与权限

首次迁移在一个事务中取得 `news_items` 的 `SHARE ROW EXCLUSIVE` 锁，阻止并发写入，允许普通读取；随后回填历史计数、安装触发器和授权，一起提交，避免回填与新写入之间出现间隙。

- 锁等待上限 5 秒，单条语句上限 180 秒。180 秒不是整个迁移的总时长上限。
- 首次失败会回滚事务；未完成的对象不会作为空日历发布。
- 完成标记、触发器或约束不完整时拒绝重跑；已完成的迁移重跑只校验和授权，不重新回填计数。
- 汇总表启用 RLS；reader 只获 SELECT，writer 通过触发器维护，不获直接写汇总表权限。
- 触发函数以可信 owner 的权限执行，固定 `search_path=pg_catalog` 并显式限定表的 schema；撤销 PUBLIC、reader、writer 的直接函数执行权限。

## 测试

本地回归：

```sh
npm test
npm run backend:typecheck
npm run backend:test
npm run news:smoke
npm run build
```

真实 PostgreSQL 行为测试在新建的隔离临时数据库中执行：

```sh
bash ops/test-calendar-postgres.sh agent-build-postgres full
```

运行器使用唯一 `navigate_calendar_test_…` 库名；夹具要求该前缀且原表为空。它复用既有 `navigate_readonly` / `navigate_writer`，不创建或修改共享集群角色，退出时删除本次创建的临时库。覆盖历史回填、重复迁移不重建、同 ID UPSERT、正文更新、日期／层级／来源变化、零计数恢复、删除、事务回滚、TRUNCATE、计数异常时写入原子性、权限、锁超时回滚以及同一计数键的并发写入。CI 使用独立 PostgreSQL 16 服务创建测试角色后执行同一运行器。

性能探针只读公共接口，发送 5 个并发请求，核对结构、计数、并发结果一致性和每个请求耗时：

```sh
node ops/verify-calendar-performance.mjs http://127.0.0.1:5196 cold-start 2500 21003
node ops/verify-calendar-performance.mjs http://127.0.0.1:5196 cache-expired 2500 21003
```

最后一个参数须换成独立核对的当前文章总量。`phase` 只是报告标签，不会自动制造冷缓存：第一轮须在 API 重启、就绪检查完成后作为首批日历 HTTP 请求运行，不做 HTTP 预热。主动模式已在监听前完成初始化；还须无访问等待超过 5 分钟，确认持续后台刷新时首访仍快。默认请求时刷新模式另需验证 60 秒 TTL 过期。不要清空共享主机或 PostgreSQL 的系统缓存。公网和真实浏览器还需验证首次打开、分类／日期切换、加载更多、详情及返回列表。

## 发布与回退

窄发布入口为 `ops/publish-calendar.sh`，已通过数据库、通用代码和 TypeScript 审查：先执行迁移并只读核对原表与汇总一致，再替换 API 读取源码并仅重启 `navigate-content-api.service`，首个日历请求通过性能门槛后完成发布。无需更改前端资源、采集定时器、Nginx 或其他应用。

发布失败应恢复备份的源码并重启本 API。新增汇总属于附加数据库对象，保留以供核查；回退的旧 API 仍可读取原始文章。不得为回退删除新闻、改动其他应用或反复清缓存制造快读结果。
